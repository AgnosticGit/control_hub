# Организации, проекты, окружения и вход через Google

## Цель

Karbird должен стать рабочим пространством для команд. Организация объединяет
людей и проекты. Доступ к проекту выдаётся отдельно от членства в организации.
Каждый проект содержит одно или несколько окружений, например Development,
Staging и Production. Личный кабинет должен сделать эту модель понятной с
первого входа и оставлять быстрый переход в наблюдаемость выбранного окружения.

## Границы работы

В поставку входят:

- организации, их участники и приглашения;
- назначение участника организации на конкретные проекты;
- создание проекта сразу с несколькими окружениями;
- Project hub и новые настройки организации и проекта;
- Google OAuth с безопасным связыванием аккаунта по подтверждённому email;
- доставка приглашений через Resend с домена `karbird.com`;
- миграция существующих проектов и участников.

В поставку не входят отдельные права на окружение, удаление окружений и
автоматическое связывание нескольких организаций между собой.

## Модель данных

```text
User
  └─ Organization membership (owner | admin | member)
       └─ Organization
            ├─ Project
            │    ├─ Project membership (owner | admin | operator | viewer)
            │    └─ Environment (Development | Staging | Production | custom)
            └─ Organization invitation
```

`projects.tenant_id` становится идентификатором организации. Новые таблицы:

- `organizations`: идентификатор, имя, дата создания;
- `organization_memberships`: пользователь, организация, организационная роль;
- `project_memberships`: пользователь, проект, проектная роль;
- `oauth_identities`: провайдер, стабильный subject Google, пользователь,
  проверенный email и дата привязки;
- `organization_invites`: хэш одноразового секрета, email, роль в организации,
  список назначений на проекты, срок действия, пригласивший пользователь.

Текущие `tenants` мигрируют в организации с теми же ID. Для каждого текущего
членства в проекте миграция создаёт организационное членство и эквивалентное
проектное назначение. Поэтому существующие scope, telemetry, токены, архивы и
ссылки продолжают работать без переноса ClickHouse-данных.

## Авторизация

Все операции с проектом проверяют два условия: пользователь состоит в
организации проекта и имеет требуемую проектную роль. Окружения наследуют роль
проекта. Системный администратор сохраняет системные полномочия, но не становится
обычным участником каждой организации.

Создатель организации получает роль `owner`; создатель проекта автоматически
получает роль `owner` в этом проекте. Организационный owner/admin может назначать
проекты, но доступ к телеметрии получают только после проектного назначения.

## Первый запуск и создание

После регистрации, включая регистрацию через Google, запускается мастер:

1. название организации;
2. название первого проекта;
3. список окружений.

В мастере предложены Development, Staging и Production. Каждое можно удалить,
переименовать или дополнить произвольным окружением. Создание выполняется одной
транзакцией. После завершения пользователь попадает в Project hub, откуда может
открыть окружение или сразу перейти к инструкции подключения SDK/agent.

Последующие проекты создаются из Project hub той же формой. У каждого нового
окружения свой ingestion token и независимая страница Integration.

## Интерфейс

`/app` становится Project hub:

- в верхней панели: переключатель организации, поиск, создание проекта, профиль;
- в боковой навигации: Projects, People, Organization settings;
- в основной области: проекты, состояние Production, число окружений, активных
  сервисов, последний полученный сигнал и быстрые действия;
- карточка проекта раскрывает окружения с их статусом данных.

Внутри выбранного окружения есть компактный переключатель
Organization / Project / Environment. Настройки проекта содержат Overview,
Environments, Members, Integrations и Project settings. Настройки организации
содержат People, Projects, Invitations и Organization settings.

Существующая страница выбора окружения и автоматический переход при одном
проекте заменяются Project hub. Карта, таймлайн и прочие наблюдаемые данные
остаются scope-подвязанными к выбранному окружению.

## Google OAuth

API предоставляет начало и callback OAuth 2.0 Authorization Code с PKCE. Для
каждой попытки создаётся короткоживущий одноразовый state, привязанный к PKCE
verifier и безопасному пути возврата. Callback обменивает code на токены,
проверяет `iss`, `aud`, подпись и `email_verified` Google ID token и сохраняет
только provider subject и необходимую идентификационную информацию.

Если identity уже привязана, создаётся обычная Karbird session. Если identity
новая, но есть аккаунт с тем же подтверждённым email, она привязывается к этому
аккаунту и вход продолжается. Если аккаунта нет, он создаётся без пароля и
пользователь проходит мастер. Вход по паролю остаётся доступен для аккаунтов с
паролем; Google не завершает действующие сессии и не изменяет пароль.

Production callback: `https://<DOMAIN>/api/v1/auth/google/callback`. Для
развёртывания Google Cloud OAuth client должен содержать этот URI. Конфигурация
включается только при наличии `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`.

## Почта через Resend

Письма отправляются сервером API по HTTPS в Resend. В первую поставку входят
приглашения в организацию и проект. Отправитель задан конфигурацией, например
`Karbird <team@karbird.com>`. В базе нет API-ключа Resend и нет необработанных
invite secrets: хранится только хэш одноразового секрета.

Ошибки Resend не создают доступ без принятого приглашения. Интерфейс показывает
статус неотправленного приглашения и даёт администратору повторить отправку,
не раскрывая секрет ссылки в списках или аудит-логе.

## Конфигурация и деплой

Добавляются только server-side переменные:

- `KARBIRD_GOOGLE_CLIENT_ID`;
- `KARBIRD_GOOGLE_CLIENT_SECRET`;
- `KARBIRD_GOOGLE_REDIRECT_URL`;
- `KARBIRD_RESEND_API_KEY`;
- `KARBIRD_MAIL_FROM`.

Значения из старого `C:\Development\auction\carbird-api\.env` используются
только как источник для GitHub Secrets/Variables или локального gitignored
`.karbird` файла. В код, compose-файлы, логи, OpenAPI и чат они не попадают.
`deploy-config.mjs` переносит значения в рендеримый `.env` с правами 600;
workflow получает их из GitHub Secrets.

## Ошибки и безопасность

- Google OAuth отвергает отсутствующий, просроченный, использованный или чужой
  state, неверный PKCE, неподтверждённый email и неверные claims.
- Все OAuth callback ошибки завершаются возвратом на login с безопасным общим
  сообщением; поставщик не раскрывает существование аккаунта.
- Приглашение принимается только пользователем с тем же email, на который оно
  выпущено, и только до истечения срока.
- Создание окружений валидирует имена и уникальность внутри проекта.
- В аудите фиксируются создание/изменение организаций, проектов, окружений,
  назначений и отправка/принятие приглашений без секретов.

## Тестирование

- Rust unit/handler: миграция, границы ролей, атомарное создание организации и
  проекта, OAuth state/PKCE/claims/linking, Resend payload without secrets.
- Integration: tenant isolation, доступ участника организации без проекта,
  доступ после назначения, создание нескольких окружений, Google identity flow
  с тестовым provider и приглашение через тестовый mail transport.
- Web vitest: модель Project hub, мастер, роли и состояния интерфейса.
- Playwright: регистрация → мастер → несколько окружений → переключение;
  приглашение человека → принятие → видимость только назначенного проекта;
  вход Google для нового и уже существующего email.

Перед завершением должны пройти `just check`, `just test`,
`just test-integration` и `just test-e2e` при запущенных `just dev` и
`just demo`.
